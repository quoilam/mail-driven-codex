# mail-oo 设计

状态：真实邮件“新建 → 结果 → 直接回复继续 → 结果”已跑通，两轮结果均由用户确认收件；退出登录及唤醒后的长期行为继续观察。更新：2026-09-26。

本文记录访谈中已确认的行为。真实邮件观察见 [邮件验证记录](mail-validation.md)，实施步骤见 [实施计划](implementation-plan.md)。

## 目标

在当前 Mac 上提供邮件驱动的 Codex 入口：从 163 邮箱接收指令，为新邮件创建 Codex 会话，为后续回复恢复原会话，每轮结束后将最终答复发回指定 QQ 邮箱。

不需要流式输出、接收确认（ACK）或排队通知。第一版只处理正文，不将附件作为输入，也不自动发送生成文件或 diff 附件。

## 部署与账户

| 项目 | 已确认约定 |
| --- | --- |
| 运行位置 | 当前 Mac，登录后自动启动 |
| 休眠行为 | 允许延迟，唤醒后补收邮件 |
| 收件账户 | 配置中的 `MAIL_USERNAME`，例如 `your-address@163.com` |
| IMAP | `imap.163.com:993`，TLS |
| 允许的发件人及固定结果收件人 | 配置中的同一个 QQ 地址 |
| 实际客户端 | 网易邮箱大师 Android；样本标识 `MailMasterAndroid/7.26.1_(16)` |
| Codex 权限 | 沿用用户已配置的 YOLO、完全开放沙箱模式 |
| Codex 模型 | 所有新建和恢复会话统一指定 `gpt-6-luna`，不自动切换其他模型 |
| 调度 | 全局串行，一次执行一封任务邮件 |
| 单轮超时 | 默认 60 分钟，可配置 |

凭据放在被 Git 忽略的 `.env`，文件权限为 `0600`；已有部署也可继续使用 `.local/config.json`，其目录权限为 `0700`。授权码不写入文档、源码或日志，不提交、上传或随邮件发送；在线仅用于认证。服务读取时会检查文件权限。

用户为降低成本指定 Luna，配置记录为 `gpt-6-luna`。新建及恢复都必须显式使用该模型，不能依赖全局默认值，也不允许静默回退到其他模型。本机 Codex 的新建与恢复调用已成功验证该标识；不可用时报告错误。本文不将“最便宜”作为已核实的定价结论。

SMTP `smtp.163.com:465` 的 TLS、EHLO、账号认证和真实投递已验证。用户对首封结果邮件的直接回复证明首封结果已到达 QQ，并确认第二封结果已收件且正确引用了首轮输入。

只接受指定发件人。执行授权同时检查地址、顶层 `Received` 的接收服务器与唯一 `Authentication-Results` 的认证服务器标识一致，以及 QQ 域名的有效 DKIM 签名。真实往返中观察到两种不同的 163 接收主机名，因此不固定具体主机名。其他来源忽略，不执行，也不向其发送报错。

## 命令与目录

新建命令放在**邮件标题**，正文是 prompt。这取代访谈早期“正文第一行写命令”的约定。

```text
标题：/new example-project
正文：请概述这个目录的内容
```

此邮件应在 `~/Documents/example-project` 下创建并运行新会话。

| 标题 | 行为 |
| --- | --- |
| `/new` | 使用 `~/Documents` |
| `/new path` | 使用 `~/Documents/{path}`；目录不存在则创建 |

路径必须解析到 `~/Documents` 内，需处理 `..`、符号链接及尚不存在的子目录，不能只检查字符串前缀。第一版采用相对路径，不接受跳出根目录的路径。

该限制约束会话初始工作目录；在完全开放沙箱模式下，它不是 Codex 的文件访问隔离边界。

无关联的新邮件必须显式使用 `/new`，否则向固定 QQ 地址报告格式或关联错误。空 prompt 不启动任务。路径可含空格；引号作为普通字符，不做 shell 式解析；命令不区分大小写。

## 会话关联

持久化保存一个内部会话编号、Codex session ID、工作目录，以及所有相关收件和结果邮件的 Message-ID。

处理顺序：

1. 校验来源并检查邮件是否已处理。
2. 优先通过 `In-Reply-To` 查找已知会话；无匹配时，从 `References` 中查找已知祖先邮件。
3. 回复字段无法关联时，使用标题中服务生成的会话编号兜底；支持显式 `/resume 编号` 手动恢复。
4. 无关联且确为新的 `/new` 指令时创建会话。
5. 无法关联的回复报错，不猜测会话，也不因为回复标题带有 `/new` 就新建会话。

`References` 必须提取 `<...>` 形式的 ID，不能按空格切分：真实样本中相邻 ID 没有空格。不同字段或显式编号指向不同会话时不猜测，报告冲突。

结果邮件需生成并持久化自己的 Message-ID，设置 `In-Reply-To` 和 `References`，并在标题携带会话编号。之后用户正常点击“回复”即可继续。

`/resume` 与 `/new` 一样位于标题，格式为 `/resume ABCDEF1234`，正文全部作为 prompt。

## 正文提取

优先读取 MIME `text/plain`，没有纯文本时将 HTML 转为文本；不重复拼接纯文本和 HTML 两个版本。

当前客户端的样本规则：

- 纯文本的历史引用以独立行 `---- 回复的原邮件 ----` 开始，并包含原信发件人、日期、主题等信息。
- HTML 历史引用位于 `.ntes-mailmaster-quote` 容器中。
- HTML 签名样本为 `#imail_signature.ntes-signature`。

只将本轮新增内容交给 Codex。提取时结合结构识别引用，避免仅因 prompt 中提到分隔字符串就截断。第一版支持正文顶部新增回复，不保证在历史引用中逐段插入回复的提取效果。对无法可靠提取的格式应报告问题，不把整个历史线程当作新指令执行。

当前规则仅有网易邮箱大师 Android 的真实样本支持，不宣称覆盖其他客户端。

## 执行与结果

后台持久化入队，全局串行执行。新任务创建 session，后续任务显式恢复对应 session，不能依赖“最近一个会话”。本机 `codex exec --json` 的 `thread.started` 事件、最终答复输出和 `exec resume` 已通过实际新建与恢复验证。

每封有效任务邮件对应一轮执行和一封最终结果邮件。正常完成发送最终答复；启动失败、执行失败、中断或超时发送可理解的原因。本地保存诊断日志，日志不作为常规邮件内容。

超时后终止该轮运行及其受控子进程，保留 session 记录。恢复任务前需确认上一轮已停止；如果 Codex 尚未生成 session ID，则不能声称可以恢复该会话。

## 持久化与故障恢复

建议使用 SQLite 保存以下信息，具体表结构在实现中确定：

| 数据 | 用途 |
| --- | --- |
| 邮箱游标 | 邮箱标识、UIDVALIDITY、已入库 UID 位置 |
| 收件记录 | UID、Message-ID、来源、规范化输入、任务状态 |
| 会话 | 内部编号、Codex session ID、工作目录 |
| 邮件映射 | 收件及结果邮件的 Message-ID → 会话 |
| 发件队列 | 固定 Message-ID、收件地址、内容、发送状态和重试信息 |

首次启动以启动时的邮箱位置建立基线，并索引历史邮件的 Message-ID，不执行历史邮件。后续重启从持久化位置补收。已读状态不参与任务判定；读取使用只读邮箱和 `BODY.PEEK`。

任务入库成功后再推进游标，避免收取中断造成漏任务。使用 UIDVALIDITY 和 UID 标识邮箱内邮件，并用 Message-ID 辅助防重。UIDVALIDITY 变化时从新 UID 空间重新扫描，并跳过已索引的历史 Message-ID；旧数据库缺少历史索引且 UIDVALIDITY 已变时暂停处理，等待人工核对。

```text
已入队 → 执行中 → 执行完成/失败 → 结果待发送 → 已发送
              ↘ 中断/超时 → 通知待发送 → 已发送
```

- 未开始的任务：重启后继续排队。
- 执行中被中断的任务：不自动重跑，通知用户，由下一封回复决定后续动作。
- 已结束但未发出结果的任务：只重试发送，不再次执行 Codex。
- IMAP 断线：重连后根据游标补收。
- SMTP 故障：保留发件队列并重试；邮件渠道本身不可用时，通过本地日志保留诊断信息。

SMTP 在“对端已接收，但本地还没记成功”时存在结果不确定的窗口。重试保留相同 Message-ID，但不能保证收件端绝不出现重复结果邮件；实现与文档不承诺端到端恰好一次。
